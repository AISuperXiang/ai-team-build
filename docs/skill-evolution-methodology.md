# Skill Evolution Methodology

## 目标

将已有 Skill 从“目录完整或提示词很长”升级为“模型可路由、按需加载、可执行、可验证、可持续改进”的能力包。此方法适用于单个 Skill 深度审查和多个 Skill 批量盘点。

审计器默认只做静态分析，不自动执行目标 Skill 的 `npm test`、网络调用或任何有副作用的脚本。验证命令只会被发现并写入报告，由调用者在确认环境后执行。

## 评审顺序

1. **定位与边界**：确认 Skill 解决的单一任务族、明确触发词、相邻 Skill 的分流条件和不适用场景。
2. **上下文效率**：检查 `SKILL.md` 是否只保留路由、决策和入口；将领域细节、长参考和模板下沉为一层可直接加载的引用。
3. **执行协议**：检查输入、成功标准、阶段、停止条件、失败处理、升级规则和最终产物是否形成闭环。
4. **自由度匹配**：高变任务使用原则；易错或高风险动作使用明确脚本、参数、前置条件和禁止项。
5. **协作边界**：只有独立且无共享写入冲突的工作可并行；每个角色必须拥有问题边界、证据要求和输出契约。团队 Skill 还必须把工作流成员视为候选池，在执行前形成 `rolePlan`，明确 `active`、`consulted` 或 `not_applicable`、场景依据和参与阶段。
6. **验证与证据**：验证等级应匹配结论。静态检查、自动化测试、运行时验证和生产观测不能互相替代。
7. **安全与可移植性**：检查硬编码绝对路径、凭据、未授权外部执行和不可移植的环境假设。
8. **演进闭环**：将失败样例、常见误用、验收场景、回归测试和维护触发条件写入 Skill，而不是只留在对话里。

由 `ai-team-build 0.6.0+` 生成的团队还应读取 `team-spec.snapshot.json`、`generation-manifest.json` 和结构化任务反馈。先聚合重复信号，再更新规格并使用 `--upgrade`；不要直接覆盖带 Git、workspace 或受管文件漂移的目录。

## 优先级规则

| 优先级 | 含义 | 处理方式 |
| --- | --- | --- |
| P0 | 安全、数据损坏、未授权副作用或不可恢复风险 | 停止发布，先修复 |
| P1 | 无法路由、无法执行、无验证、结论不可信 | 作为发布阻断项 |
| P2 | 高概率漏步骤、上下文浪费、角色冲突或不可维护 | 当前迭代修复 |
| P3 | 可读性、补充案例或可选能力 | 排入后续优化 |

## 升华循环

1. 运行 `scripts/audit-skills.js` 获取基线评分、发现、证据与建议验证命令。
2. 先处理 P0/P1，再选择一个 P2 改进切片；不要在没有证据时大规模重写。
3. 修改时保持原 Skill 的职责边界，优先增加可验证的门禁、模板、脚本或验收场景。
4. 运行目标 Skill 已声明的验证命令，并把命令、结果、未覆盖范围写入审计报告或交付摘要。
5. 复跑审计；只有发现关闭或被明确接受，才标记为完成。

## 审计维度

`audit-skills.js` 按 100 分输出以下维度：

- 发现与边界：frontmatter、触发条件、负向路由和输入输出。
- 上下文与加载：入口长度、最小加载、按需引用和职责分层。
- 执行与协作：工作流、停止条件、风险分级、角色/文件边界、失败处理，以及团队角色是否具备可重评的 `rolePlan` 与 N/A 规则。
- 验证与证据：测试入口、验证脚本、验收场景、证据与结论等级。
- 安全与可移植性：绝对路径、疑似凭据、未授权副作用边界。
- 演进与维护：版本、维护规则、失败样例、回归和改进闭环。

评分只能说明静态设计质量，不能替代目标仓库的运行时验证。

## 基准来源

- OpenAI Agent Skills 指南强调：Skill 应以清晰的 `name`/`description` 被发现，并通过按需加载、明确输入输出和可运行的脚本保持可复用性。
- Anthropic Skill 最佳实践强调：保持 `SKILL.md` 精简、按任务脆弱度设定自由度，并用真实使用场景和多模型验证。
