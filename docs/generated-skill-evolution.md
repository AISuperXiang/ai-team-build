# Generated Skill Evolution

## Goal

Keep generated team Skills reproducible and upgradeable without deleting Git metadata, task workspaces, or local extensions.

## Generated Sources

Every generated team contains:

- `team-spec.snapshot.json`: the validated generation input.
- `generation-report.json`: generation, scoring, governance, and verification metadata.
- `generation-manifest.json`: SHA-256 and byte length for every factory-managed file.

The manifest does not manage `.git/`, `node_modules/`, workspace task directories, or other local files that were not generated by the factory.

## Upgrade Workflow

Preview an existing generated team:

```bash
node scripts/generate-team-skill.js \
  --spec <generated-team>/team-spec.snapshot.json \
  --output <generated-team> \
  --upgrade \
  --dry-run
```

Apply only when the plan has no conflicts:

```bash
node scripts/generate-team-skill.js \
  --spec <updated-team-spec.json> \
  --output <generated-team> \
  --upgrade
```

The upgrade planner:

1. Generates the candidate version in an isolated system temporary directory.
2. Compares the previous manifest, current files, and candidate manifest.
3. Preserves untracked files and Git metadata.
4. Blocks before writing when a managed file was modified or deleted locally.
5. Updates, creates, or removes only unchanged managed files.
6. Backs up touched files and restores them if the update fails.

Generated teams from versions before `0.6.0` do not have a trusted manifest. Generate the new version to a separate directory, review the diff, and adopt it manually once. Future upgrades can then use `--upgrade`.

## Overwrite Boundary

`--overwrite` is retained for automation that owns a disposable generated directory. For an existing directory it requires:

- A valid manifest for the same skill id.
- No `.git` directory.
- No modified or missing managed files.
- No untracked files that would be deleted.

Use `--upgrade` for maintained repositories.

## Feedback Loop

Generated teams include `assets/templates/iteration-feedback.json` and `scripts/summarize-feedback.js`.

After completed or abandoned tasks:

1. Record outcome, user acceptance, rework, role signals, friction, evidence gaps, missing capabilities, and suggested changes.
2. Aggregate multiple records with `npm run feedback:summary -- --input workspace/<feedback-dir> --json`.
3. Review repeated P1/P2 signals before editing `team-spec.snapshot.json`.
4. Apply approved spec changes through `--upgrade`.
5. Run `npm test`, generated validation, and acceptance contracts.

Feedback is evidence for prioritization, not proof of business outcomes.
